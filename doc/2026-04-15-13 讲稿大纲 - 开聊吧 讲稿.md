## 0. 开场：先告诉大家这 15 分钟会听到什么

先说一下今天这 15 分钟打算干嘛。

之前和相关人讨论的时候，说希望聊一下 agent。然后我也在想，agent 这玩意儿现在已经被讲得有点过于花里胡哨了，真要讲，很容易又讲成一个新焦虑源。所以我后来就换了个思路：不如整理一些最近日常里高频听说的问题，挑几个比较关键的，集中讲一讲。

所以今天我不打算讲“某个 AI 产品有多强”，也不打算讲“大家必须马上 all in，不然明天就没工作了”这种东西。最近这种叙事已经足够多了，不缺我这一份。我更想做的是帮大家把最近听到的一堆 AI 说法重新排个序，至少先把脉络理顺一点。

今天主要会聊四件事。第一，为什么最近大家会这么焦虑，FOMO 为什么一下子上来了。第二，那些看起来很厉害的 Agent，本质上到底是什么，别让一堆名词把人唬住。第三，怎么安全地使用 AI，我觉得这个优先级其实比“会不会用”更高。第四，如果时间精力有限，普通人到底该怎么学、什么适合交给 AI、未来岗位要求会怎么变化。

整体上我的立场比较简单：不是来制造焦虑的，是来稍微缓解一点焦虑的。虽然我自己是开发，但今天也不是来讲硬核技术细节的，更不是来做工具宣传。我会尽量只讲一些在真实使用里相对稳定、不那么容易过期的判断。中间如果哪里讲歪了、讲快了、讲得不对，直接打断就行。

## 1. 焦虑从哪来：为什么最近大家这么 FOMO

虽然今天名义上是来聊 agent，但我想先说一下屋里的大象：最近大家聊得最多的其实不是 agent 本身，而是焦虑，是 FOMO。

我自己也琢磨了一下，这焦虑到底是咋来的。为什么感觉从今年初开始，很多人对 AI 的体感一下子被拉高了，像突然进入另一个世界一样？

我自己的判断是，这不是突然发生的事。agent 对人类工作产生冲击，这件事情，实际上是在过去三年里慢慢发生的。只不过之前很多人，有意无意地忽略了这部分动态而已。信息虽然很多，但如果从能力发展的角度去看，其实脉络是能理清的。

大概可以把它看成一条不断叠加的演化路径。

最早其实就是基本模型加一个 LLM Client。这个阶段，已经能做很多事了：问答、改写、总结、翻译、起草、整理信息。然后再往后，是基本模型加一点代码、加一点工作流，比如 n8n 这种东西，开始能串流程。再往后，是更强一点的模型，开始有 function calling，开始能接工具，开始出现所谓 agentic 工具。再往后，是更复杂的 Agent。再到今天，很多人已经开始接触到更特化、更像“自主型助手”的东西了，包括公司里的悟空、Homiclaw 这类更贴近真实办公流和组织场景的产品。

到了这一层，人的体感会突然变化。因为它不再像一个单纯的聊天机器人了，而开始像工作系统的一部分。你会突然意识到，这玩意儿不是只能陪你聊天、改改文案，它已经开始碰真实工作流了。

所以焦虑不是凭空来的。它至少是几股东西叠在一起：

第一，模型能力确实在快速升级。

第二，工具层一直在换，而且越来越接近真实任务。

第三，人和模型之间的合作边界在变。

第四，生产关系的重构已经不只是 PPT 上的词了。

第五，也是最刺激的一点，人和人的能力差距会被这波变化迅速放大。

以前很多技术升级，往往是组织先升级，再慢慢往下传导，你还能有一点缓冲期。这次不太一样。很多能力是直接发给个人的，谁先上手，谁就先形成新的工作方式；谁没上手，就会很容易产生一种“我是不是已经被甩开了”的感觉。

所以如果你最近觉得这东西特别吵、特别密、特别让人喘不过气，这感受完全正常。不是你一个人没跟上，也不意味着你突然变菜了。更像是过去三年里慢慢发生的变化，最近半年集中显影了而已。

我这里想先做的一件事，不是继续放大这种焦虑，而是把它理顺：这玩意不是突如其来，是有发展脉络的；既然有脉络，就能拆，就能看懂，也就没必要先把自己吓死。

## 2. Agent 到底是什么：别被包装名词带着跑

然后说到 agent。

先说一句比较不政治正确的话：我个人其实不太喜欢用 “agent” 这个词。不是因为它不重要，而是因为这词儿这两年定义一直在变，而且复杂度一直在提高，导致不同人说出这个词的时候，很可能根本不是在说同一个东西。

有的人说的 agent，可能只是“模型加工具调用”；有的人说的是“多步工作流”；有的人说的是“能自己做决策、自己发消息、自己调系统的自主型助手”；还有的人说的其实只是“一个包装得比较重的聊天应用”。所以如果一上来就陷入这个词本身，特别容易鸡同鸭讲。

我更建议一个比较土、但比较管用的理解方式：把它拆开看。

最里面，唯一真正不可替代的驱动还是模型。说白了，它本体还是那个文字输入、文字输出的推理器。外面再套一层，是 Prompt。再往外，是上下文管理：你喂了什么背景，带了什么历史，补了什么约束。再往外，是工具调用的解析和处理：模型说“我要查一下”“我要发一下”“我要调一个东西”，系统怎么把这句话翻译成真实动作。再往外，是工作流编排：一步做完以后下一步干嘛。再往外，才是记忆层、状态层。最后一层，是和真实环境的对接，比如即时通讯软件、文件系统、浏览器、各种 API、定时任务。

所有你现在看到那些特别唬人的名字，什么 tool use、function calling、skills、插件、MCP、A2A，基本都能被塞回这个大纲里去。它们不是没区别，但区别通常没有宣传材料写得那么玄。

我举一个特别土的例子。假设我用 crontab 每分钟触发一次 Gemini，让它调用一个发消息能力，去给人发一句“在吗”。这玩意儿听起来是不是已经有点像“自主型助手”了？但你拆开看，它其实只是：定时触发一下、模型推理一下、调个工具、发个消息。就完了。它最唬人的地方，是“它动了”；但“它动了”这件事本身，并不一定很有魔法。

所以这一段我最想讲的是：别被包装名词带着跑。LLM 本身没有突然变成某种玄学生命体。真正越来越复杂的，是外壳，是上下文怎么组织、输出怎么解释、动作怎么落到环境里。你把这个结构看清楚以后，就不太会因为自己没跟上某个新词儿而产生一种“完了我已经掉队了”的感觉。

这也是为什么我前面说，很多所谓的 agent，本质上不是“新物种”，而是模型和外壳层一起演化到某个阶段之后，看起来像个新东西。你要真想理解它，最好的方式不是背名词，而是拆层。

## 3. 避坑和工具：合理的学习路径是什么 —— 啥玩意值得学，啥玩意值得无视

然后说到学习路径。这个话题我自己的观点其实挺粗暴的：不要先买课，不要先收集工具，也不要一上来就掉进一堆包装得很好的 AI 应用里。

我觉得现在学 AI/LLM，一个经常更优的路径，反而是先直接接触模型本身。说白了，当前顶级模型的教学能力，已经超过大多数普通课程了。所以很多时候，与其花钱买课，不如把钱拿去充顶级模型额度，让它直接交互式教你。至少你拿到的是一个活的、会根据你提问实时调整的“老师”，而不是一份可能三个月前就开始过时的录播。

然后我会建议，先从最轻的一层开始。比如直接和模型对话，先用 LLM Client 去解决一些单点问题：写月报、写纪要、改文案、总结资料、生成一版邮件草稿。这一层其实已经能覆盖很多人工作里最烦的那些碎活儿了。

等你开始有一些反复出现的套路，再往前走一点，去做小工作流。比如固定的 SOP，固定的输入输出格式，固定的资料整理流程。这时候像 Dify 这种东西会开始有意义。再往后，如果你真的有更复杂的开发诉求、自动化诉求，再去碰 coding agent，去碰更复杂的 Agent 系统。

也就是说，我觉得比较靠谱的顺序其实是：先学会和模型协作，再学会把任务变成工作流，最后再碰复杂 Agent。不要顺序反过来。

还有一个我特别想吐槽的点，就是“工具收集癖”。很多人现在的学习方式，本质上是在收藏名词和收藏 UI。今天装一个，明天装一个，最后电脑里 8 个客户端、12 个插件、17 个新概念，结果工作还是全手搓。这个路径我觉得收益很低。

判断一个东西值不值得学，我更倾向于看四个增量：有没有带来数据积累的增量，知识理解的增量，熟练度的增量，或者真实问题解决的增量。如果最后只剩下“我用了一个很新的工具”这个结果，那这东西大概率没啥必要投入太多。

顺便这里也补一个挺现实的判断：不同模型适合不同任务，不同任务适合不同 harness。你不能因为一个模型放进 Claude Code 里不够猛，就说它整个都不行。像百灵这种模型，如果硬塞进重型 coding 场景里，未必是它最舒服的位置；但如果你拿它做办公文本生成、工作邮件、会议纪要、方案初稿，其实已经绰绰有余了。所以不要用一种场景的评分标准，去全盘否定一个模型。

我自己现在其实也是混着用：LLM Client、Dify、Coding Agent，各自干各自擅长的活儿。但这不意味着所有人都要从最复杂那层开始。很多人的问题，先把 LLM Client 用顺，就已经能解决掉一大半了。

所以这一段如果只留一句话，就是：先别急着追工具，先让模型真的帮你解决一个实际问题。这个顺序对了，后面很多东西会自然长出来；顺序错了，就很容易变成在一堆名词里空转。

## 4. 什么适合交给 AI，什么不适合

前面讲了学习路径，接下来我想讲一个更实际的问题：什么适合交给 AI，什么不适合。

我觉得这里最有用的判断方式，不是问“AI 到底行不行”，而是问“这个任务适不适合 AI 接手”。这两种问法差别很大。前一种问法很容易把讨论带向空泛；后一种问法，才真正和工作有关。

这里可以借一个概念，叫 jagged frontier。它的意思是，模型能力并不是均匀分布的。它不是整体都很强，也不是整体都不行，而是会在某些任务上表现得非常强，在另一些看起来不难的地方又很容易犯错。所以问题不在于“AI 是不是万能”，而在于“这个任务的结构，是否适合交给它”。

通常来说，那些允许一定容错、方便人工校正、有 SOP、上下文也比较容易补齐的任务，更适合交给 AI。比如会议整理、纪要、周报月报、方案初稿、资料归纳，或者是在一个复杂项目里快速把聊天记录和背景信息梳理出来。这类任务的共同点是：就算第一版不完美，人也能很方便地接手修正，而不是一下子就出事故。

我自己判断一个任务值不值得交给 AI，标准也很简单：它有没有帮我节约劳动、时间、精力或者注意力；或者，它有没有替我接掉一些我本来就不太想手工做的重复劳动。如果答案是有，那通常就值得继续优化。

反过来，那些不太适合直接交给 AI 的任务，也有一些很明确的特征。比如它很难验证真假，上下文又很难完整收集，错了代价还很高，或者它天然就是高度主观、缺乏稳定标准的。像心理治疗、投资建议、未来预测、高风险拍板，这些都属于典型例子。问题不是模型一句都不能说，而是它很容易给出一种“看起来合理”的输出，但你并没有足够强的手段去验证它。

还有一类任务，我觉得特别值得单独拿出来说。很多人会把年终总结、绩效草稿、招聘辅助、复杂需求分析这类任务归到“AI 不行”里。但实际情况经常不是模型不行，而是任务没拆对、上下文没给够、约束没写清楚、校验机制也没补上。也就是说，问题不一定在模型本身，而在任务设计。

所以这一段我最想留下的判断是：不要笼统地问“AI 能不能做这件事”，而要先判断这件事的任务结构是什么、容错率有多高、是否方便人工接管、上下文能不能补齐。把这个框架建立起来以后，很多事情会清楚很多，也不容易因为试错失败就直接得出“AI 没用”或者“AI 万能”这种过度结论。

## 5. 传统非技术岗位未来还存在吗？

接下来这个问题，应该也是很多人真正关心的：传统非技术岗位未来还存在吗？

我的判断是，当然存在。但如果把问题问得更精确一点，真正该讨论的不是“这个岗位名还在不在”，而是“这个岗位原来依赖的那套能力结构，还能不能按原样维持下去”。

从现实看，产品、运营、HR、项目管理、业务分析、内容生产、销售、协调推进，这些岗位不会因为 AI 一出来就直接消失。组织里也不可能突然只剩工程师。这个事情没那么戏剧化。

但变化也确实在发生。过去很多岗位的一部分价值，来自信息差、文书整理能力、流程熟练度、长链路沟通中的中介作用，以及对各种既有格式和系统的熟悉程度。这些能力不会完全没用，但它们的稀缺性会下降。因为 LLM 对这类“可以描述、可以总结、可以改写、可以格式化”的工作，天然就比较擅长。

所以问题不在于“非技术岗位还安不安全”，而在于这些岗位里，哪些部分会被压缩，哪些部分会变得更重要。

我自己的判断是，未来很多岗位更重要的能力，会慢慢收敛到几项：你能不能定义问题，能不能把任务拆开，能不能把上下文给足，能不能约束输出格式，能不能校验结果，能不能对最后的结果负责，以及能不能和系统协作，而不是只和人协作。

这里我想特别强调一下，这不等于以后所有人都要去学命令行，更不等于所有人都要转成工程师。AI 工具操作能力会变成通用门槛，但这个门槛不一定长成“写代码”的样子。很多非常好的工具本身就不是命令行形态。真正变化的是：岗位越来越要求你把工作翻译成系统能执行的形式，同时还要能判断系统吐出来的东西到底能不能用。

所以我觉得未来的划分方式，可能不再是简单的“技术 / 非技术”。更像是：谁能稳定地使用 AI 系统完成工作，谁不能。真正比较危险的，往往不是不会写代码的人，而是既不会用 AI，也不会定义任务、不会校验结果、最后也没法对输出负责的人。

所以这件事如果要落成一句比较直接的话，大概就是：非技术岗位会继续存在，但“完全不理解系统逻辑”的传统舒适区，会越来越小。

## 6. Vibe Coding 有没有用？——如何避免浪费时间

接下来这个问题，我觉得也挺值得专门说一下，就是 Vibe Coding 到底有没有用。

我的判断是，有，而且确实有它很有价值的一面。但问题在于，它的价值主要集中在探索和原型阶段，而不是直接替代工程能力和交付责任。

如果你有一个模糊想法，想快速做个东西看看；或者你想把一个概念先转成一个能讨论的界面；或者你想让一个完全没写过代码的人先跨过“从 0 到 1 什么都没有”的门槛，那 Vibe Coding 非常有用。它能明显降低启动成本，也能提高试错速度。以前很多想法可能卡在“还没开始就懒得做”，现在至少能先出来一个雏形。

但它的问题也很明显：它很容易制造一种错觉。就是你做出了一个能跑的东西，于是会误以为自己已经做出了一个系统，甚至误以为工程问题已经被自动抹平了。

真正的问题不在“它能不能跑”，而在于你能不能审核它。你知不知道它为什么这样实现，哪里可能出错，状态怎么流动，权限怎么控制，异常怎么处理，依赖怎么管理，出了问题你能不能定位，出了事故你能不能回滚。如果这些问题接不住，那它更接近一个原型，而不是一个可交付系统。

所以如果目标是上线、交付、跑业务，关键路径通常就不再是 vibe 本身，而会回到一些很传统但绕不过去的东西：计算机组成、操作系统、网络、信息安全、软件工程，以及一整套可维护、可观测、可回滚的工程约束。这些不会因为模型很强就自然消失。

所以这一段我更想给一个比较中性的判断：不要把 Vibe Coding 看得太低，它对探索很有价值；但也不要把它看得太高，觉得它能直接替代工程能力。更准确的说法应该是：玩具级原型、探索性 demo、启发式尝试，完全可以 vibe；真正要对用户、数据、业务结果负责的系统，不能只 vibe。

## 7. 结尾：时间精力有限的人，怎么持续跟上技能更新而保持一定的精神健康

最后我想把前面这些内容收一下，不再继续加信息量，而是给几个更实际的结论。

第一，先固定一个稳定入口。对大多数人来说，找一个自己顺手的 LLM Client 长期用，比频繁切换各种新工具更重要。入口稳定之后，你才更容易积累自己的提问方式、任务模板和工作流。像 Cherry Studio、ChatWise、Jan.ai、LM Studio 这种更偏本质化的入口，都属于比较适合长期使用的类型。这里一个比较明确的避坑点是：不要长期把网页 Chat 当作唯一主力工作入口。它当然方便，但更适合轻量体验，不太适合深度沉淀工作流。

第二，先替代自己最烦的重复劳动。不要一上来就想做全自动数字员工，这个目标通常太大，也太容易挫败。更现实的路径，是先找一段你最烦、最重复、最不想自己做的工作，把这一小段替掉。比如纪要、月报、改写、整理材料。只要这一段真替掉了，你就会立刻感受到收益，也比较容易继续往前走。

第三，先理解原理，再决定要不要升级工具层。前面讲了很多名词，但最后回到一句话，就是不要被所有新名词牵着跑。基础问题，先用 LLM Client；流程开始重复，再试 Dify 这种工作流工具；真的有复杂开发诉求，再谨慎碰 coding agent。这里还有一个很现实的判断：不同模型适合不同任务，不同任务适合不同 harness。比如办公文本生成、工作邮件、纪要、方案初稿，百灵这类模型已经完全够用；没必要因为它在重型 coding 场景里不是最优，就反过来否定它在办公场景里的价值。

第四，不要高估短期变化，也不要低估长期重构。短期来看，没必要每个热点都追，晚一点学某个工具，通常不会造成决定性损失。长期来看，这轮变化确实会持续重构工作方式，和 AI 协作会越来越像一种基础能力。所以更好的目标，不是把所有热点都追一遍，而是持续把 AI 变成自己的稳定外部能力。

如果最后只留一句话，我会想留这句：与其焦虑自己没用上所有新工具，不如先拥有一个稳定、可控、真正帮你省事的个人外挂。
